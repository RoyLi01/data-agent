# 面向用户增长的可信数据分析 Agent

状态：项目设计与目标简历，尚未实现、部署或实测。以下简历采用完成态便于明确建设目标；实际投递时仅保留已经完成且能演示的内容。业务参考用户熟悉的字节用户增长场景，不代表字节内部既有系统或真实上线成果。

## 一、简历项目经历目标稿

**项目名称：用户增长智能分析 Agent**

**角色：数据开发 / 核心开发**

**技术栈：Python、FastAPI、LLM Tool Calling、MCP、Milvus、SQLGlot、ClickHouse、Pandas、PostgreSQL、Docker**

**项目背景：** 面向增长运营在渠道获客、转化及留存分析中的临时取数和连续追问需求，构建覆盖自然语言查询、指标校验、数据分析与报告生成的 Agent。结合数仓指标体系与元数据治理，重点解决指标口径误用、多表关联导致重复统计、历史查询结果被错误复用等问题。

**核心工作：**

- **指标语义与元数据建设：** 梳理注册、激活、D7 留存及渠道成本等指标，定义统计粒度、去重实体、时间窗口、成功条件及关联关系；构建字段级混合检索，在重排结果上补全指标计算与过滤依赖，减少关键字段遗漏和错误关联。
- **Agent 编排与工具接入：** 基于 Python 状态机和原生 Tool Calling 实现查询、分析双角色协作，支持任务路由、歧义澄清及中断恢复；通过 MCP 接入受控数据查询工具，以渐进式 Skills 加载查询规范和增长分析方法，约束工具范围及调用预算。
- **SQL 可靠性治理：** 基于结构化查询契约与 SQLGlot AST 校验必要过滤、字段绑定、聚合粒度及允许的关联路径，对核心指标采用受控模板；结合只读权限、执行超时和分层纠错，降低 SQL 可执行但业务结果错误的风险。
- **多轮分析与证据追溯：** 为查询结果保存粒度、字段、过滤条件、指标版本、数据时间及完整性标记，判断追问能否复用已有数据；封装渠道指标变动分解、成熟留存队列比较和图表生成能力，支持从报告结论回溯指标口径、SQL 与结果集。
- **评测与问题闭环：** 建设覆盖单表、多表、比率指标和多轮追问的回归集，分别评估结果正确率、工具参数正确率、复用决策及端到端延迟；按召回、口径、SQL 和执行错误归类，验证检索补全与语义校验的增量效果。

成果数据暂不填写。后续以真实测试集规模、基线与改进后结果正确率、P95 延迟和人工复核结果补充；不能直接使用参考资料的数据。

## 二、业务范围和典型演示

首版覆盖注册、成功激活、渠道获客成本和 D7 留存，服务增长运营的取数、对比与追问。不尝试回答所有经营问题，也不把描述性指标分解写成因果归因。

建议演示一个完整会话：

1. “比较最近两个完整周的信息流渠道激活成本，找出变化最大的渠道。”系统通过工具解析日期，确认激活成本口径，查询花费与成功激活量，输出明细和口径。
2. “给我画趋势图。”如果前次仅查询两周汇总，缺少逐日粒度，需要补查；如果已经保留完整日粒度数据，则直接绘图。不能只凭语义相似度决定复用。
3. “再按操作系统拆开。”检查历史结果是否包含操作系统；缺失则生成新查询，不让模型凭空拆分。
4. “这些渠道的 D7 留存也下降了吗？”按注册 cohort 查询，并根据数据完成水位排除未成熟队列，另行展示可比范围。

另外演示两条容易出错的情况：用户未定义“新增”且存在注册/激活两种口径时澄清；上游数据延迟时指出数据未齐，不直接解释为业务下滑。

## 三、技术选型及边界

| 层次 | 拟议选型 | 作用 |
|---|---|---|
| 服务与编排 | Python、FastAPI、Pydantic、自定义状态机 | 接口、结构化输入输出、状态迁移、暂停与恢复 |
| 模型 | 支持原生 Tool Calling 的模型，经本地评测后固定版本 | 任务理解、计划、SQL 草稿、分析解释；不预先宣称某模型最优 |
| 元数据检索 | Milvus、Embedding、Reranker | BM25 与稠密向量召回，RRF 融合，原问题重排 |
| 查询校验 | SQLGlot + 指标注册表 + 规则校验 | 解析 SQL、字段与过滤校验、受控指标模板 |
| 数仓与查询 | ClickHouse | 存放模拟增长明细、汇总和指标服务表；实际企业上游引擎按已有系统接入 |
| 工具协议 | MCP | 服务端发现与调用查询工具，隔离数据库凭据 |
| 会话与元数据 | PostgreSQL | 状态、指标版本、任务、结果引用、评测日志 |
| 结果存储与分析 | Parquet、Pandas、图表库、受限 Worker | 小规模结果分析及绘图；大数据聚合下推数据库 |
| 部署 | Docker Compose | 开发演示部署；代码 Worker 需额外落实网络、资源和文件权限限制 |

Milvus 的 BM25 与稠密向量混合检索能力可参考[官方文档](https://milvus.io/docs/multi-vector-search.md)。不同时引入 Elasticsearch、Faiss、pgvector 等重复组件。没有必要为了 Agent 项目重新造一套 Kafka/Flink 实时链路；若后续确有实时增长需求再增加。

## 四、执行流程

用户问题 → 会话约束恢复 → 新查询/已有结果分析/澄清路由 → Schema 检索与依赖补全 → 查询契约 → SQL 生成与校验 → MCP 查询 → 结果登记 → 分析 Skill → 带证据的回答。

Coder 负责取数，Analyst 负责对结果分析。两者可以使用同一个模型，但拥有不同的工具、提示词和状态；不做多个角色自由聊天。主流程、权限检查、预算、终止条件由程序固定，模型只在许可范围内决定工具与步骤。

建议状态为 `RECEIVED / ROUTED / NEEDS_CLARIFICATION / PLANNED / VALIDATED / EXECUTING / ANALYZING / COMPLETED / FAILED`。保存任务 ID、状态版本、查询契约、步骤依赖、已完成结果和失败类型。恢复接口要求匹配版本与请求幂等键，避免用户重复提交导致重复执行；恢复后重新检查权限与数据版本。

工具结果采用统一信封：状态、数据引用、Schema 版本、数据水位、耗时、错误类型。每轮工具调用经过参数校验和预算扣减；超预算后返回已完成结果及明确失败原因。

## 五、把数仓经验转成 Agent 的可靠性

### 1. 指标注册与字段依赖补全

为每个指标保存：业务定义、事实表、统计实体、粒度、分子分母、成功状态、时间字段、观察窗口、允许维度、关联路径、负责人和版本。

字段检索得到候选后，再确定性补全指标依赖。例如“成功激活用户数”除了用户 ID，还必须包含成功状态和激活时间；“信息流渠道 CPA”还必须携带渠道分类、花费、成功激活量与关联键。不能让这些字段因 Top-K 排名低而消失。

候选可裁剪无关描述，但不能静默丢弃必需依赖。依赖数量超过预算时，拆分任务或限定指标范围。元数据检索本身也按当前身份过滤。

### 2. 查询契约与独立校验

AskData 已有 `query_contract`。本方案扩展为包含 cohort、去重键、观察窗口、数据水位及版本的业务约束。例如 D7 留存约束应明确：

```yaml
metric_id: registration_d7_retention
metric_version: v1
cohort: registration_date
entity: user_id
dimensions: [channel_id]
numerator: cohort_users_active_on_day_7
denominator: registered_cohort_users
maturity: day_7_partition_complete
ratio_aggregation: sum_numerator_divided_by_sum_denominator
```

窗口是某自然日还是注册满 168 小时、活跃事件如何定义，都必须在注册表定清，不让模型自行选择。日期由工具结合时区解析。

关键区别：不能只让模型同时生成合同和 SQL，再让它判断二者一致。核心约束来自可信指标注册表与已确认的用户意图，程序再检查 SQL 是否满足。检查范围包括字段绑定、必需过滤、聚合方式、关联路径和已登记的基数限制。SQLGlot 提供解析能力，业务校验由我们实现，它不会自动证明任意 SQL 的语义正确。

核心指标优先把模型输出的结构化参数编译到经验证模板；自由 SQL 用于受限探索，并明确校验覆盖范围。多事实表先按目标粒度各自聚合后再关联；比率用累计分子/累计分母，不平均每日比率。分母为零、空数据、延迟和不完整队列单独处理。

### 3. 数据分层

模拟事实至少包含注册、激活、活跃、广告花费；维表包含渠道、活动、设备类型。设计注册事实、激活事实和用户日活明细，再形成渠道日汇总与注册 cohort 留存表，最后服务指标查询。

明确不同事实的身份与粒度：广告花费可能只到活动日，不能凭空分配到用户或操作系统；若缺少可靠映射，系统说明维度不可用或请求约定分配方法。用户渠道归属应固定归因规则与快照，不能用当前用户属性覆盖历史事实。

增长质量检查包括主键唯一、枚举有效、关联覆盖、分区完成水位及汇总对账。涉及转化与留存的约束要基于同一队列，不能对不同日期事件总量强行套用大小关系。

## 六、Skills、MCP 与分析结果

### Skills

沿用资料渐进式加载：元数据用于路由，命中后读取正文，再按需加载脚本和参考定义。每项配置声明工具白名单、参数结构、最大调用数和允许动作，由调度器执行。

- `growth_query`：指标口径、日期解析、Schema 依赖和查询模板。
- `retention_compare`：成熟队列选择、留存对比、分母与样本量展示。
- `channel_change_analysis`：注册/激活/成本指标对比及贡献分解。
- `growth_report`：结论、数据范围、图表、证据和限制说明。

总体转化率变化可选用对称分解：若 R=Σwᵢrᵢ，则 ΔR=Σ[(wᵢ₁+wᵢ₀)/2]Δrᵢ + Σ[(rᵢ₁+rᵢ₀)/2]Δwᵢ。它把变化分成渠道内部转化率和结构权重两部分，仅用于口径一致、渠道可比且比率可定义的集合；新增、退出或零分母渠道单列。计算由固定函数完成，模型只解释结果，不称其为因果证明。

### MCP 与查询边界

模型只能调用当前身份获准的查询工具；服务端从认证上下文读取身份，不能信任模型提交的用户 ID。执行端检查数据库与表列权限、只读 AST、SQL 方言、超时和结果大小，数据库账号同样只读。行级范围通过可信视图或服务端强制约束实现，不能仅依靠提示词。

权限覆盖检索、执行与历史结果读取三个入口。MCP 负责接口协议，具体认证授权需要自行实现。执行超时必须支持底层取消；仅让接口等待超时不能保证查询已经停止。

### 结果资产与会话记忆

每张结果保存 `artifact_id、query_id、columns、grain、filters、date_range、metric_version、schema_version、data_watermark、row_count、is_truncated、owner_scope、expires_at`，另存完整结果位置和来源 SQL。

路由时只加载这些描述，按字段覆盖、可聚合粒度、过滤范围、完整性、新鲜度与权限判断能否复用。渠道汇总不能回答设备细分；只有 Top10 的结果不能用于总体占比；只展示前 200 行时，分析工具也不能误把预览当完整数据。

记忆保存已确认口径、时间、过滤和结果引用。聊天摘要用于恢复背景，不覆盖结构化口径。长期保存的模板与偏好需要明确来源，历史结果每次读取仍检查权限和时效。

常见统计先用固定函数。确需模型生成 Python 时，在独立 Worker 中执行，限制网络、CPU、内存、进程数、时长和文件路径；输入只读，不提供数据库凭据，执行结束清理临时目录。不能把 `exec` 加黑名单称为沙箱。

## 七、错误处理与评测

| 错误 | 处理 |
|---|---|
| 字段不存在、版本过期 | 更新 Schema、重检索和重规划 |
| SQL 方言或类型错误 | 将精简错误交给 Coder，有限修复后重新验证 |
| 缺失必要过滤、粒度冲突 | 回到契约/计划层，不只改 SQL 语法 |
| 超时或服务暂不可用 | 在预算内重试或缩小经允许的查询范围，不悄悄改变业务问题 |
| 数据缺失、未成熟队列 | 标记分析不可用或明确展示可用范围 |
| 合法空结果 | 返回零行与筛选范围，不自动当作查询失败 |

评测先独立定义标准答案与业务语义，再生成问题表述。开发集用于调提示词和 few-shot，测试集保留；不能把测试 SQL 放回检索示例库。

对比组：基础 Schema+LLM；加入混合检索；加入依赖补全；再加入契约检查与受控模板。模型版本、问题和资源设置保持一致。分别记录字段召回与精确率、全部必需依赖覆盖率、SQL 执行率、结果正确率、澄清决策、复用决策、答案证据一致性、端到端 P50/P95、Token 和查询开销。

结果比较需考虑行顺序、数值容差和允许的展示辅助列；业务关键的过滤与队列定义也要检查，不能只碰巧对上小样本数值。设计能揭露错误的对抗数据：多条激活记录、失败激活、渠道重名、事实关联放大、未成熟 D7、Top-N 截断、历史权限变化。

## 八、实施验收顺序

1. 建立模拟增长数据、分层模型、指标注册表和人工正确 SQL；先验证数仓口径。
