## 1. 本文要解决什么问题

在你自己的 Data Agent 基础上，整理值得继续增强的能力，说明为什么做、在哪里做、依赖什么、怎样验收。核心定位是：**面向分层数仓，能够理解指标口径、选择合适数据模型并解释查询依据的数据分析 Agent。**

项目服务于数仓岗位求职和工程学习。用户增长是第一条演示业务链，使用模拟数据；不把模拟场景描述为已经在字节生产环境上线。

本轮仅整理文档，不修改业务代码、不安装新组件、不启动增强功能开发。

## 4. 各增强项如何落地

### E01：真实模型联调（移出本轮范围）

遵照最新范围决定，不安排真实模型端到端联调、效果基准或模型消融，不要求提供 API Key 才能开始后续开发。已有模型接口保留。

E14/E15 的真实自然语言生成与模型纠错仍依赖模型服务；没有配置时明确提示不可用。开发中使用的模型响应桩仅验证链路与错误处理，不能代表真实模型效果。

### E02：元数据、字段画像与知识库增强

**已有基础：** 当前 `catalog.py` 已有表/字段/指标/关系块；字段已有三视图。应扩充已有结构，而不是再建立一套平行知识库。

**建议工作：**

1. 将可维护的业务配置从 Python 常量逐步迁移到经过结构校验的 JSON/YAML，保留稳定 ID 和向后兼容读取。
2. 表模型增加层级、业务过程、粒度、主键、时间语义、可用维度、刷新方式和认证信息。
3. 字段补充类型、业务含义、角色、单位、业务别名、样例、空值率、不同值数、枚举分布和时间/数值范围。画像记录采集时间、快照、样本量及全量/抽样方式，只作为理解线索；不同值数等统计不得将样本值标成全表精确值。
4. 表说明 chunk 表达模型用途，指标 chunk 表达定义和可计算范围，字段 chunk 保留父表上下文。按结构组织，不随意按字数切断口径与关联键。
5. 仅为语义视图计算向量；关键词与重排分别使用相应文本。
6. 用内容哈希、Schema 版本、Embedding 标识维护索引一致性；支持局部更新和失效删除。

**候选位置：** 修改 `catalog.py`、`schema.py`、`retrieval.py`；拟新增 `metadata/`、`data_agent/metadata_loader.py` 和画像脚本。以上新增路径尚不存在。

**验收：** 明确物理字段名和业务同义表达都能检索；只变更一个模型时定位到相关文档；删除字段不会继续进入计划；样例只展示允许的数据。

**边界：** 有字段画像不代表自动理解业务定义；枚举、指标口径和 Join 语义仍需人工确认。当前只采集本地登记的模拟数据，不新增元数据管理权限系统。画像生成、Schema 变更检测与索引更新应可重复执行。

### E03：指标语义与粒度规则

**已有基础：** 五个登记指标具有规则、依赖、单位和时间可加性；SQL 模板已体现去重、分子分母及队列成熟期。

**建议工作：** 增加结构化的指标版本、时间锚点、去重实体、固定过滤、分子分母、观察窗口、允许维度、可加维度，以及可用物理实现列表。

| 示例 | 必须保持的规则 |
|---|---|
| 注册人数 | 按用户首次注册日期统计；注册渠道和注册 OS 是快照维度 |
| 周期活跃人数（拟新增） | 请求周期内对 user_id 去重；不能累加日活得到月活 |
| 成功激活人数 | 当前按成功事件发生日过滤，再按用户去重；跨日计数不可随意相加 |
| 注册七日激活率 | 按注册队列计算，不能解释成某日激活人数/某日注册人数 |
| D7 留存率 | 注册后第 7 自然日活跃；须处理尚未观察完整的队列 |
| CPA | 花费与激活分别聚合到兼容粒度后计算；不凭空按 OS 分摊花费 |

比率只有在口径、分组范围和分子分母的可聚合条件均满足时，才允许汇总分子分母后重算，不能平均百分比。去重分母也不能因保存了一个计数值就任意求和。

**候选位置：** 扩展 `catalog.py`、`models.py`、`query.py`；拟新增 `data_agent/metric_semantics.py`。

**验收：** 每个首批指标都有明确契约和独立参考结果；对日活求和当月活、比率直接平均、跨口径混算等反例能给出拒绝或重查理由。

### E04：真实分层数仓加工链

以自己项目的 `users`、`activity`、`channels` 为第一批输入，保留现有模拟数据。先构建独立的加工输出，再接入查询，不直接改写现有表。

| 拟建模型 | 粒度 | 主要用途 |
|---|---|---|
| `ods_user` | 输入用户记录 | 保存演示源快照和来源版本 |
| `ods_activity` | 输入用户日活跃记录 | 保存已有源数据；不把它声称为未经处理的点击事件日志 |
| `dim_channel` | 每渠道一行 | 渠道名称、类别等维度 |
| `dwd_user_registration` | 每用户首注一行 | 注册日期、渠道、注册 OS |
| `dwd_user_activity` | 每用户每天一行 | 周期活跃去重的明细基础 |
| `dws_channel_registration_day` | 日期＋渠道 | 日注册统计；在首注唯一归属下支持跨日汇总 |
| `dws_channel_activity_day` | 日期＋渠道 | 日活统计；不直接用于月活计数相加 |
| `ads_channel_growth_month` | 月份＋渠道 | 按已确认口径加工完整月份的注册/活跃结果 |

每个模型配套实际 SQL、依赖、唯一键和数据检查。ADS 月活必须由周期明细去重或等价的可验证方法产生，而不是累加 DWS 日活。

当前项目的 OS 来自注册用户快照，可用来演示“汇总缺维度，转向明细”；不沿用 AskData 的 platform 字段名，避免混淆两套数据模型。活跃指标若按 OS/渠道分组，第一版明确采用注册归属，不冒充活跃发生时设备或渠道归因。

加工支持重建、重复执行一致性与日期范围说明。后续如增加迟到数据和回补，需同步更新快照及下游完整性状态；第一版不承诺完整调度系统。

**验收：** 汇总与独立明细基准核对一致；重跑不翻倍；粒度唯一键成立；异常数据样例能够触发检查；原五个指标回归不退化。

### E05：类型化关系图与血缘追溯

将关系明确拆为：

- `join`：关联键、连接方向/基数、是否需要时间有效区间。用于合法 Join。
- `derives_from`：加工依赖。边保存 `upstream_model` 和 `downstream_model`，图方向统一为上游到下游；从下游查源头时反向遍历。
- `implements_metric`：模型或输出字段实现哪个版本的指标。

记录加工 SQL 路径、版本、来源和验证时间；首批关键字段记录输入字段与转换表达式。先人工核对明确的加工 SQL，再决定是否增加自动解析。

**候选位置：** 保留 `schema.py` 的 Join 逻辑，拟新增 `data_agent/lineage.py`、`metadata/lineage.json`，不将加工边混入原有 Join BFS。

**验收：** 可追溯 ADS 指标到加工 SQL 和上游字段；能发现无效引用与意外循环；数据源回退不越权；血缘存在但语义不匹配时不自动选用。

### E06：数仓感知选表与明细回退

RAG 负责发现候选；选表器基于结构化契约进行检查。建议固定以下顺序：

1. 读取请求中的指标版本、时间区间、维度、过滤、精度要求与执行身份。
2. 校验候选是否实现相同口径、是否具备所需维度与过滤字段、是否能够合法汇总到目标粒度。
3. 检查权限、日期覆盖、分区完整性和快照状态。
4. 在合格候选之间比较认证状态和预估扫描成本；若没有真实成本统计，只标记为启发式估算。
5. 没有合格汇总模型时，沿有权限的血缘查找明细候选，并重复上述检查。
6. 无可用数据源时返回具体限制或澄清问题，不能选择“最相关但不正确”的表凑出结果。

**拟新增输出 `SourcePlan`：** 请求契约、选择的数据模型及版本、选用的指标实现、必要字段、允许的聚合方式、候选拒绝原因、回退路径和数据完整范围。

模型可以帮助解释候选，但不能改写权限和已登记语义。层级不作为硬优先顺序；匹配口径且完整的明细，比口径错误的 ADS 更合适。

**候选位置：** 拟新增 `data_agent/source_planner.py`，扩展 `models.py`、`engine.py`、`query.py`。先让注册与拟新增活跃指标使用新路径，其他指标继续走现有编译器。

**验收：** 相同指标多张表时有可验证选择；缺 OS 时转明细；月活不错误使用日活计数；汇总不完整、过期或无权限时给出正确分支。

### E13：元数据发现——按字段找表与目录查询（待开发）

**用户需求：** 在聊天框中输入“哪些表包含 user_id”“找 DWD 层同时包含用户 ID 和渠道 ID 的表”，得到可核对的表清单。查询对象是表、字段及其说明，不是业务数据行；“找包含 status 字段的表”和“找 status 值为 success 的记录”属于不同任务。

**当前基础与缺口：** 自己的 `catalog.py` 已登记表字段，`/api/catalog` 可返回目录，但聊天路由尚无专用元数据意图及筛选工具。AskData 的 `/api/schema`、`/api/schema/search` 可作为目录与检索设计参考；后者的相关性召回不能证明已完整列举所有匹配表。此处记录的是拟开发功能，不代表两个项目的聊天入口已通过验收。

#### 1. 第一版范围和匹配语义

| 请求 | 匹配方式 | 结果要求 |
|---|---|---|
| 哪些表包含 `user_id` 字段 | `exact`：完整字段名相等 | 返回授权目录快照内全部匹配表，数量大时分页 |
| 字段名中带有 `user` 的表 | `contains`：字段名包含指定文本 | 明确是名称子串匹配，不是业务语义相似或字段值匹配 |
| 同时包含 `user_id` 和 `channel_id` 的表 | `all`：同一张表满足所有条件 | 不能把分别具有两个字段的不同表拼成一个命中 |
| 含 `user_id` 或 `channel_id` 任一字段的表 | `any`：满足任一条件 | 去重返回表，并列出具体命中的字段 |
| 找 DWD 层的表 | 层级筛选叠加字段条件 | 使用登记的 `layer`，不只根据表名前缀猜测 |
| 哪些表有用户标识 | P2：业务别名和语义候选 | 展示匹配依据；候选含义不一致时澄清，不承诺语义召回穷尽所有表 |

第一版先实现精确/子串、单字段/多字段及目录范围筛选。表层级、业务域等条件依赖 E02 的元数据登记；当前五张表没有登记的层级不得编造。大小写与标识符规范化规则由元数据来源明确，不无条件将所有数据库字段名转小写。首版子串按字面处理，不默认支持任意正则或 SQL 通配符。

#### 2. 确定性筛选与 RAG 的分工

```text
自然语言请求＋必要的元数据追问上下文
              ↓
metadata_search 意图＋结构化筛选条件
              ↓
确定调用身份及可见目录范围
              ↓
精确字段/名称子串 → 直接筛选完整元数据目录
业务同义表达     → 别名/混合检索/重排 → 确认字段含义 → 目录筛选
              ↓
表去重、稳定排序和分页 → 展示匹配字段、模型说明和证据
```

精确查询不走 RRF、重排阈值或 Top K 截断，不把检索返回的前几个字段当成全部答案。语义检索用于发现可能对应的字段；每个候选保留表与字段的稳定 ID，不能因一个表的 `uid` 表示用户就认定所有同名字段都表示用户。结果需区分“明确匹配”与“语义候选”。

“完整”仅相对于当前身份可见、已登记的指定目录快照，不代表所有外部数据库。输出目录来源、版本和更新时间；元数据过期或采集范围有限时说明边界。无匹配时返回“当前可见目录中未找到”，不编造字段，也不透露其他身份可见的资源数量。

#### 3. 路由、工具与结果契约

拟新增 `MetadataSearchRequest`，字段包括：`field_terms`、`match_mode`（exact/contains/semantic）、`field_operator`（all/any）、数据源/库/层级/业务域范围、分页参数。语义模式作为后续扩展；结构化条件需校验，实际权限范围取自服务端身份，不能由模型扩大。

拟新增工具 `find_tables_by_fields`。首版从现有目录适配器读取，不扫描业务行、不临时采样、不让模型生成任意系统表 SQL。以后通过受控适配器同步外部数仓目录，仍沿用相同筛选契约。新工具需登记到 MCP、技能白名单与调用预算，并在实际执行端复核权限。

返回建议包含：库与表的稳定 ID、表名、命中字段及说明、匹配依据、表用途、已登记的层级与粒度、元数据版本/更新时间、可见匹配总数、分页信息和是否还有下一页。总数仅统计当前身份可见的命中；分页游标绑定筛选条件和目录版本，目录变化时提示重新查询，避免漏项或重复。

多轮示例：“哪些表有 user_id”→“只看 DWD”→“还要有 channel_id”。保存独立的元数据筛选状态，最后一步默认追加 AND 条件；用户明确说“改成”时替换字段条件。状态中记录本轮变更，语义不明确时澄清。不得把上一轮的 CPA 指标、日期条件或业务结果复用逻辑套入该请求；权限变化后重新校验。

“这些表从哪里加工而来”是后续 `trace_lineage` 请求，依赖 E05；按明确表 ID 追溯。存在 Join 关系不等于存在加工血缘，字段同名也不证明可以直接关联。

**候选修改位置：** `context.py`、`planner.py`、`models.py`、`engine.py` 接入路由和状态；拟新增 `data_agent/metadata_search.py` 实现筛选；`catalog.py`/E02 目录适配器供数；`gateway.py`、`mcp_server.py`、`skills/` 接入工具；`api.py`、`static/index.html` 展示目录结果。新增路径和类型均为计划命名，尚未创建。

#### 4. 验收与演示用例

以下期望只针对当前五表目录；扩展数仓模型后应更新固定快照的参考集合。

| 场景 | 期望 |
|---|---|
| 精确查 `user_id` | 返回 `users`、`activations`、`activity`，不返回其他表 |
| 同时包含 `user_id` 与 `channel_id` | 只返回 `users` |
| 包含 `user_id` 或 `channel_id` | 返回当前五张表，各表只出现一次 |
| 查询不存在的字段 | 返回空集合及可见范围说明，无业务 SQL 执行 |
| 字段名子串、多字段、明确范围组合 | 与独立人工标注的目录匹配集合一致 |
| 匹配表数超过单页大小或 RAG 的 Top K | 遍历各页得到完整集合，无遗漏与重复 |
| 限制本地登记目录范围 | 结果及总数只涵盖配置的可见表；不开发不同用户/角色的权限系统 |
| 业务查询后问“哪些表有 user_id” | 切换元数据路由，不继承旧指标，不要求填写指标时间范围 |
| 未登记层级时要求 DWD | 说明层级信息不足，不根据名字猜测；完成 E02 后按真实登记值筛选 |
| “用户标识”对应不同实体 | 展示候选依据或澄清；不自动认定用户 ID、设备 ID、会员 ID 等价 |
| 修改/删除字段后再次查询 | 采用新目录版本；旧会话或缓存不继续展示已删除字段 |

精确筛选和规则路由可以先离线实现，不依赖模型 Key；语义模式复用现有别名和检索接口。没有真实模型调用记录时，自然语言泛化状态保留为未实测，不另安排模型验证专项。记录目录匹配、分页与路由的实际软件测试结果，不预先填写准确率或效率提升。

**依赖与顺序：** E13 精确匹配可基于当前目录先做，并接入 E07 最小路由；E02 提供版本、范围及层级增强；E11 贯通执行身份和工具权限。语义扩展在精确匹配验收后推进，来源追溯等待 E05，不把完整血缘开发作为“按字段找表”的前置条件。

### E14：查询范围扩展与受控 SQL 生成（待开发）

**目标：** 从五个登记指标扩展为登记数据集内的自然语言查询，保留原指标模板路径。不是直接开放任意数据库、任意 SQL 或写入操作。

| 查询类型 | 拟支持示例 | 关键条件 |
|---|---|---|
| 明细与筛选 | 上周通过搜索渠道注册的用户明细 | 明确字段、日期、过滤、排序与条数限制 |
| 分组聚合与排行 | 各渠道注册人数、播放量最高的十条内容 | 去重实体、分组粒度、Top N 及并列排序规则 |
| 多表关联 | 各投放计划的花费与归属注册用户数 | 使用登记关联、明确归因，避免事实表直接 Join 放大 |
| 时间趋势 | 最近四周的日活趋势 | 事件时间、时区、日期边界与数据完整性 |
| 同比/环比 | 本月与上月同一观察范围的注册数及变化 | 明确对比区间、未完整月份处理和零分母规则 |
| 复杂只读查询 | CTE、条件聚合、窗口函数排行 | 当前数据库方言支持，函数和资源边界经过校验 |

**设计路径：**

1. 复用上下文聚合，把问题转为 `QuerySpec`：查询类型、目标字段/指标、过滤、时间、分组、排序、行数及已确认口径。缺少会影响结果的条件时澄清。
2. 根据元数据 RAG 与关系图得到候选表、字段和合法关联；涉及同指标多层模型时使用 E06。一般明细查询不要求伪造指标版本，不强行进入五指标契约。
3. 已登记指标且请求兼容模板时，沿用模板编译；其他支持的查询交给模型生成结构化 SQL 提案。提案说明使用的表字段和关联依据，但模型自述不作为正确性证明。
4. SQL 经解析、单条只读检查、库表及字段绑定、函数/表达式限制、必要业务规则检查后，由独立的通用查询工具执行。禁止未知表、外部读写、管理命令和不受控函数，限制执行时间和返回行数。
5. 返回 SQL、列名、数据行、完整性/截断标记、目录与数据版本及执行证据。截断结果明确为预览；登记指标结果与通用结果采用可区分的类型，通用结果不进入原五指标分析/复用流程。
6. 校验或执行失败时进入 E15；不存在合适模型或口径无法确定时澄清/返回限制，不靠删条件制造成功。

**模块建议：** 扩展 `models.py`、`planner.py`、`engine.py`、`query.py` 和 MCP 工具；拟新增 `data_agent/sql_agent.py`。保留 `Contract` 与 `query_metric`，新增 `QuerySpec` 及通用查询结果类型，避免破坏现有 API 消费方。

**验收：** 支持类型都有独立参考 SQL 和预期结果；真实数据库执行与参考值一致；越界 SQL 被拦截；原指标行为保持；未配置模型时自然语言生成路径明确提示不可用。固定模型响应只用于链路测试，不声称验证任意自然语言理解。

### E15：SQL 纠错与有限重试（待开发）

**目标：** 在 E14 生成 SQL 出错时提供结构化反馈，支持模型修复，不将“能执行”作为业务正确的充分条件。

```text
SQL 提案 → 静态校验 → 数据库执行 → 成功返回
              ↓错误        ↓错误
       错误分类＋原请求＋原 SQL＋相关 Schema
                         ↓
                  判断是否允许修复
                         ↓
             修复提案 → 重新校验 → 重新执行
```

- 可修复错误：语法错误、已登记字段的拼写/歧义绑定、当前方言支持的函数替换、GROUP BY 等类型/聚合错误。只能在原请求和登记 Schema 范围内修复。
- 不自动绕过：禁止表/操作、工具白名单、权限拒绝、缺失业务口径。不存在所需字段时明确说明或澄清，不能替换为含义不同的字段。
- 超时与暂时故障：分别分类；默认返回明确失败，不通过缩小日期、减少分组或添加业务过滤来伪造成功。资源优化如后续支持，必须保持语义并受独立预算约束。
- 修复预算：默认首次提案后最多修复两次，实际还受剩余模型/工具调用预算限制；每次校验、执行及修复均记录。相同规范化 SQL 与相同错误再次出现时提前停止，避免无效循环。
- 条件保持：时间、显式过滤、指标定义、去重、粒度和排序要求作为约束保留。可检查的条件由程序校验；程序无法证明任意 SQL 语义等价，无法确认时不得将修复标为成功完成业务任务。
- 证据：保存原 SQL、错误类别、反馈、修复 SQL、尝试序号和最后状态；错误信息只保留必要数据库诊断。没有模型服务时保留错误并明确无法自动修复，不伪造修复记录。

**模块建议：** 拟新增 `data_agent/sql_repair.py`，在 `engine.py` 编排，在 `query.py` 输出结构化错误，在 E11 新查询工具执行所有最终校验。继续使用 Python 状态机，不引入 LangGraph。

**验收：** 用语法错、字段歧义、方言错误、禁止操作、重复失败、预算耗尽等用例验证分支；注入“删除过滤条件才执行成功”的修复提案，必须拒绝或中止。固定错误与修复响应验证控制流程，不替代真实模型纠错效果验证。

**目标：** 除当前增长指标外，增加渠道投放、内容运营数据，使 E14 的查询范围有真实可执行的数据支撑。使用自己生成的可复现模拟数据，AskData 作为结构参考，不要求照搬 41 张表。

**模块建议：** 扩展 `seed.py`、`metadata/` 与 E04 加工脚本；新增场景数据生成和参考查询目录。目录均为计划，不表示已创建。

## 5. 第一版目标架构

```text
用户问题 + 当前会话 + 主动选择的记忆
                  ↓
上下文聚合、任务意图、结构化请求
                  ↓
        信息不足 → 澄清并恢复
                  ↓
元数据查询 → 目录筛选/语义候选 → 表清单与匹配依据（独立返回）
解释/追溯/已有结果分析 → 对应工具与证据
                  ↓ 需要取数
检索表模型、指标、字段候选
                  ↓
登记指标/多层模型 → 选表器校验口径、粒度、维度与完整性
一般明细/聚合查询 → 在登记 Schema 与关联范围内形成 QuerySpec
                  ↓
涉及汇总回退时按加工血缘寻找其他来源，并再次校验
                  ↓
确定数据源及合法 Join / 聚合方式
                  ↓
登记指标 → 模板编译；其他支持查询 → 模型生成受控 SQL
                  ↓
SQL 校验、MCP 只读执行 ← 可修复错误 → 有限修复后重新校验
                  ↓
现有表格/文本输出：结果、SQL、选表依据、血缘及修复记录
                  ↓
保存结果版本与短期记忆；长期记忆仍由用户主动保存
```

图表示计划中的目标流程，不能据此声称当前已存在选表器或加工血缘模块。

## 7. 第一版验收故事

按同一条会话演示，比零散展示组件更能说明项目价值：

1. 问“上个月各渠道注册人数”：使用口径匹配、数据完整且合适的模型，结果与独立基准一致。
2. 追问“再按注册时操作系统拆开”：发现已选汇总缺 OS，转向有权限的注册明细。
3. 追问“为什么这次用了明细表”：引用本轮 SourcePlan，说明缺维度原因。
4. 新问题“上个月各渠道活跃人数”：使用明确的周期活跃口径，避免每日去重计数求和。
5. 查看来源：展示指标定义、当前模型与上游加工 SQL，不能混用两个请求的证据。
6. 改变测试水位或访问范围：不完整/无权限来源被排除；如果所有来源都不满足，明确返回限制。
7. 更新元数据后继续查询：原有版本检查拒绝错误复用；通用 SQL 请求走独立结果路径，不扩展记忆能力。
8. 查询“上周搜索渠道注册用户明细”和“注册人数最多的十个渠道”：分别验证通用明细及聚合排行。
9. 在受控测试中注入字段/语法错误：展示有限修复与再次校验；删除原过滤条件的修复被拒绝。
10. 第二、三批数据完成后查询计划成本及内容播放排行，与参考 SQL 结果对账；不增加新的分析交互。

另设元数据发现演示：问“哪些表包含 user_id”→“只看 DWD”→“还要有 channel_id”→“这些表的上游是什么”。前三步验证 E13 筛选及 E07 条件继承，最后一步在 E05 完成后验证血缘；层级未登记时应明确提示，不提前演示为已支持。
