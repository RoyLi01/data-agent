# 基于 AskData 的数仓语义与血缘增强方案

> 范围更新：本文件保留此前“基于 AskData 二次开发”的讨论。用户当前要求先规划自己现有 Data Agent 的增强，后续开发主体、优先级和验收以 [Data Agent 增强规划](DATA_AGENT_ENHANCEMENT_ROADMAP.md) 为准。

日期：2026-09-25。状态：设计方案，尚未实现以下新增数仓能力。

## 项目定位

暂定名称：面向分层数仓的数据问答与分析 Agent。

面向短视频用户增长的模拟业务，解决同一指标存在多个候选表时如何选对数据源、遵守粒度与指标口径，以及结果不足时如何回到可用明细重新取数的问题。新增能力的主要贡献是数仓建模和查询决策，不以修改项目名称作为独立成果。

原始 AskData 位于 `../askdata_studio_ops_release`，作为阅读和对照基线；现有 Data Agent 是独立实现。后续增强版应在独立开发副本中推进，保留来源说明与变更记录，避免混淆三者的完成状态。继续遵守用户“不使用 LangGraph”的要求：参考 AskData 的业务逻辑，以 Python 状态机实现增强版工作流。

## 已核对的基线

- AskData 的 `_schema.json` 包含 41 张表、276 个字段、53 条关联关系。
- 字段文档融合表描述、样例、数据画像，使用关键词、语义、重排三种文本表示。
- `retrieval/graph.py` 按已登记 Join 关系寻找路径，补齐连接键。
- `schema_layers` 描述表级、字段级、数据级信息，不是 ODS/DWD/DWS/ADS 分层。
- 原版提供会话、问数/问答路由、MCP、Skills、记忆及权限相关模块；具体正确性需要在改造时逐项验收。
- 目前这些关系主要描述 Join，不应直接当作加工血缘。

## 核心设计

### 一、模型与指标元数据

表级模型登记：模型 ID、数仓层、业务过程、一行代表什么、唯一键、时间语义、可用维度、可计算指标、刷新方式、完整数据截止时间、口径版本、认证状态及访问范围。

指标登记：指标 ID、业务定义、时间锚点、去重实体、过滤条件、允许维度、按时间/维度的可加性、口径版本、可用物理实现。汇总比率需保留分子分母；日去重人数不能直接当成月去重人数求和。

层级和认证状态不是正确性的证明。先检查指标语义、粒度、维度、权限、分区覆盖和数据完整性，符合条件后再比较成本、认证状态等偏好。

### 二、三类图关系分开维护

| 关系 | 语义 | 用途 |
|---|---|---|
| join | 可按哪些键、基数和时间条件关联 | 生成查询连接约束 |
| derives_from | 下游由哪些上游加工产生 | 寻找明细来源、追溯加工过程 |
| implements_metric | 模型或字段实现哪个指标口径 | 找到指标的可用计算入口 |

血缘采用上游到下游的有向关系，记录加工 SQL 路径、版本和来源；字段级补充输出字段、输入字段与转换表达式。第一版人工核对 SQL 后登记，暂不声称全自动 SQL 血缘解析。

不能将血缘边作为 Join 边交给现有 BFS。沿血缘找到候选明细后，必须重新进行选表校验，并保持同一访问范围；无权限或无法确定时澄清/拒绝，不越权回退。

### 三、RAG 与确定性选表配合

新增表模型文档、指标文档，保留字段文档。RAG 用于发现候选和理解业务描述，结构化登记表用于作出不可跳过的判断。

流程：请求聚合 → 指标/维度/时间契约 → 候选模型检索 → 硬性兼容检查 → 合格候选排序 → 按需展开血缘 → Schema/Join 上下文 → 查询执行 → 结果与选表证据。

每个候选保留选择或拒绝原因，例如：不支持 platform 维度、日去重指标不可按月相加、口径版本不同、完整水位不足、没有读取权限。不存在合格候选时不能让模型随意选择一个表。

执行前限制 SQL 引用到已批准的数据源；对首批登记指标优先使用可验证的计算规则。不能声称仅靠 AST 或表白名单就证明任意模型 SQL 的指标口径正确。

## 第一条可复现的增长数仓链

优先使用源码已有 `user_registrations`、`user_daily_activity`、`acquisition_channels` 数据，新增独立加工结果，不把原来的 `growth_daily_metrics` 改名后直接当作已验证的 DWS。

| 拟建模型 | 粒度与作用 |
|---|---|
| ods_user_registration | 保留原始注册记录与源字段 |
| ods_user_daily_activity | 保留原始活跃记录 |
| dim_acquisition_channel | 每渠道一行，登记渠道属性 |
| dwd_user_registration | 拟定成功注册口径，按用户保留确定的首条有效注册，保留注册 platform 和归因渠道 |
| dwd_user_valid_activity | 有效活跃的用户日粒度，去重后用于周期活跃人数计算 |
| dws_channel_registration_day | 每日每渠道注册人数；基于首注唯一归属才能按天汇总 |
| dws_channel_activity_day | 每日每渠道活跃人数；月活禁止对其日计数求和 |
| ads_channel_growth_month | 基于同一明细口径加工的月度增长结果；登记支持维度与覆盖范围 |

落地前必须核对 registration_status 等字段实际枚举、注册归因方式、重复记录、异常时间及测试数据的一致性，明确默认口径。上述是拟建模型和语义，不是对当前数据质量的断言。

源数据提供注册 platform，可作为第一版“缺维度转明细”的示例。暂不用 `user_devices` 直接给注册明细加设备维度：一个用户可能有多设备，需要先定义注册时设备或归因策略，避免一对多放大。

## 验收场景

| 问题/条件 | 预期行为 | 核验方法 |
|---|---|---|
| 上个月各渠道注册人数 | 选择满足口径且月份完整的 ADS，或对兼容 DWS 合法汇总 | 和 DWD 独立基准计算核对 |
| 再按注册平台拆开 | ADS/DWS 缺维度时寻找可访问 DWD 并重新取数 | 断言选择来源和结果分组 |
| 上个月各渠道活跃人数 | 使用匹配月口径的模型或明细去重，禁止日活直接求和 | 构造跨日重复活跃用户 |
| 汇总层少更新一天 | 排除不完整汇总；仅在明细覆盖完整且允许时回退 | 修改测试水位并核对原因 |
| 汇总与明细指标口径版本不同 | 不混用；没有匹配来源时澄清或报无法满足 | 测试不同版本配置 |
| 只有汇总读取权限 | 不沿血缘越权读取 DWD | 校验选表与执行两端权限 |
| 多事实表直接 Join 导致倍增 | 按登记粒度先聚合或拒绝不安全连接 | 构造重复关联键 |
| 为什么使用这张表 | 返回指标口径、粒度、拒选原因与 SQL 来源 | 检查报告证据结构 |

评估分别记录候选覆盖、数据源选择、路由/回退、查询结果和权限拦截；先构建基准，再测试增强效果，不提前填写提升百分比。

## 实施顺序与源码入口

1. **数据模型与口径**：核对源字段，编写加工 SQL、模型元数据和独立对照计算。
2. **检索知识与选表器**：参考 `retrieval/service.py`，增加表/指标文档及兼容性检查，输出选择证据。
3. **类型化关系图**：拆分 Join 与 lineage；参考 `retrieval/graph.py`，只按需展开有权限的上下游。
4. **执行集成**：参考 `preprocessing.py`、`services/askdata_service.py`、`workflows/query_graph.py` 的流程，以原生 Python 状态机组织，并测试澄清恢复。
5. **前端与评测**：沿用能复用的展示思路，增加候选表选择理由、血缘来源、数据完整性；再进行真实模型联调。

学习时每次只跑通一个真实问题，展示输入、候选、拒选原因、选定模型、SQL 和结果。模型、字段与类命名清楚，继续使用易读排版和基本中文注释。
